# Localisation (i18n)

The kiosk runs **one locale per terminal**, chosen by the country pack
(`country.pack` in `config.yaml`). There is no locale routing,
no negotiation and no translation library — the layer is a message catalog
per pack and a `t()` helper (`<kiosk>/frontend/src/lib/i18n.ts`) that works
identically in client components and API routes, because the flow engine
speaks the same instructions the screens show. The one runtime exception is
the chat kiosk's **spoken-language detection** (below), which lets the
conversation — not the UI chrome — follow the language a citizen speaks.

## Changing the entire UI language

The whole kiosk — screens, flow instructions, prompts, speech — speaks the
language its country pack was written in. To change it:

1. **Translate (or pick) a country pack.** The pack owns every localised
   surface: the message catalog (`messages.ts`), the STT vocabulary and
   repair examples (`speech.ts`), the
   prompt variables — including `language_instruction`, which a non-English
   pack MUST set (e.g. `"\nAlways reply in Vietnamese."`) or the assistant
   answers in English — and the whole `services/` tree with its labels,
   questions and step copy. The `add-country-pack` skill and
   [country-packs.md](country-packs.md) carry the full checklist.
2. **Set the config keys** in `config.yaml`: `country.pack`,
   `locale.language` and the other `locale.*` formats, and a
   `voice.tts.voice` that can actually speak the
   language (see the voice inventory in
   [configuration.md](configuration.md#spoken-languages-chat-mode)).
3. **Restart.** `country.pack` and `locale.*` are read at startup and served
   to the browser with the page, so a production build or packaged app picks
   them up without rebuilding. A pack that is not yet registered in
   `<kiosk>/frontend/src/packs/index.ts` *is* a code change, and does need a build.

Strings not yet extracted into the catalog (the generic shell copy — see
the cut-line below) ship in English; translating everything means extending
the catalog first.

## Spoken-language detection (chat mode)

Set `voice.languages` in config.yaml (mapping language code → voice; see
[configuration.md](configuration.md#spoken-languages-chat-mode) for the
voices each language gets) to let the chat kiosk follow the language a
citizen speaks without any control on screen. Per spoken turn:

1. Whisper detects the language of each utterance itself
   (`voice.stt.language: auto`, the default), transcribes in it, and says
   which one it heard. The kiosk takes its word for it — there is no
   classifier of its own. The studio's OEP backend reports the language
   (`verbose_json`); on OVMS or MERaLiON, which do not, the session keeps
   its language.
2. A language the kiosk speaks becomes the session's. One it speaks a close
   relative of instead is taken as that one: Whisper writes some Malay as
   Indonesian (and the reverse), and on large-v3 some Mandarin as Cantonese.
   Any other language is far more often Whisper misjudging a short or noisy
   utterance than a citizen speaking it, so the utterance is transcribed
   again in the session's language and stays in it. The session language
   rides on every chat turn — spoken, typed, a tapped option or chip, an
   upload — as message metadata, so the reply to a tap stays in it too.
3. The conversational prompts get a per-turn
   `{{language_instruction}}` — `Always reply in <language>.` — so the LLM
   replies (and the live captions, which just render the reply) follow the
   citizen. That includes the pack's own language, so a citizen who switches
   back is answered in it; only a translated pack's own
   `language_instruction` stays in charge there. The turn's `[kiosk]` lines
   end by naming the language again, nearest the reply: a small model told
   only in the system prompt keeps writing in the language the history is
   in. The reply follows the citizen's latest words, not their first.
4. Narration reads each reply in the voice configured for the language it
   was written in — on whichever studio text-to-speech instance speaks it
   (Kokoro for its eight languages, Malaya, Pocket TTS, VieNeu and
   Fastspeech2-HS for Malay, Indonesian, Vietnamese and Tamil). Every reply
   is the model's own, a step of a service as much as small talk: it relays
   the flow's `say` and asks the step's question, options included, in the
   citizen's language. The chat route stamps that language on the reply
   (`metadata.language`; `narrationLanguage` in `use-chat-voice.ts`), so a
   reply keeps its voice after the citizen switches. The step's own ask text
   and option labels are pack copy, so narration reads them after a reply
   only in the pack's language (`speakableText` in `use-chat.ts`).

Every session starts back in the pack's language. Detection degrades to a
no-op when the recognizer names no language.

What deliberately does **not** follow the citizen: the `t()` catalog and
all shell copy, the flow engine's instructions and buttons on screen (the
step overlay, option labels, receipt cards), typed-only
turns (no detection runs on the keyboard path — the composer keeps the
session language a spoken turn established). Routing free text in a detected
second language rides on the chat agent alone. Known rough edges: the transcript-repair
vocabulary pass still runs (proper-noun aliases are language-neutral) but
the LLM repair step is skipped outside the pack's language; the live-caption
splitter is Latin-punctuation-based and degrades for scriptio-continua
scripts; and Whisper's own detection can misjudge a very short utterance — a
one-word answer may come back in a neighbouring language's spelling, or as
another language the kiosk lists, which then becomes the session's (list
only the languages visitors speak). A deployment that only ever hears one
language can pin `voice.stt.language`.

## The cut-line: what goes through `t()`

Deliberately not every string. The catalog holds only what a country pack
must own — text that names the country's documents, agencies or procedures:

- the ID-reader instructions (`src/lib/id-reader.ts` — they name the MyKad),
- card-reader failure copy (`api/_lib/nfc.ts`),
- identity-document labels and the reader step card
  (`services/shared/steps/identity.tsx`, `flows/engine.ts`,
  `components/chat/chat-kiosk.tsx`).

Generic shell strings — "Back", "Processing…", step plumbing sentences —
stay hardcoded English until a translated deployment actually exists;
extracting them buys nothing while every pack ships English. When that day
comes, extend the catalog: `MessageKey` derives from the Malaysia catalog
(`src/packs/malaysia/messages.ts`), so every pack is compile-checked to
cover whatever keys exist.

Other pack-owned text lives beside the catalog rather than in it, keyed by
its consumer: system-prompt variables (`pack.promptVars` — filled into the
`{{country_adjective}}` / `{{id_document}}` / `{{language_instruction}}`
placeholders in `api/_lib/prompts.ts`), the STT repair vocabulary and
examples (`pack.speech`).

## Formatting

- `src/lib/format.ts` — money/date/clock rendering reads the `locale:`
  block (`money_locale`, `date_locale`, `clock_locale`, `currency`); every
  default is the value that used to be hardcoded. `plural()`/`countOf()`
  are English morphology — copy in another language writes full phrases
  into its catalog instead of calling them.
- Fonts in `(kiosk)/layout.tsx` load the `latin`, `latin-ext` and
  `vietnamese` subsets. `next/font` requires literal subsets — they cannot
  come from config — so add a script there when a pack needs one.

## What is intentionally still English/Malaysian

The staff enrolment desk, the Payload admin UI, the registry's domain
vocabulary (license classes, race/religion enums, road-tax bands) and the
test suite. See the checklist in [country-packs.md](country-packs.md) for
what a new country actually needs.
